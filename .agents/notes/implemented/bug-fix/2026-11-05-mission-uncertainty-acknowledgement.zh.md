# Agent Note: 不确定性确认只覆盖它当时看到的疑问，被挤出窗口的调用只是「仍未结束」

Status: implemented

[English](2026-11-05-mission-uncertainty-acknowledgement.md) | 中文

## 问题

在宽扇出得到约束之后（见[上一篇记录](2026-11-04-mission-recovery-resilience.zh.md)），
`dsh-mission-continuity` 仍留下两个缺陷。两者都在修改前的源码上先复现，再动手修复。

**一次确认等于整场赦免。** 人工对未知结果的裁决只以一条标记的形式写在*可丢弃的发现索引行*上——
`lastError.code = 'uncertain-acknowledged'`——而 `supervisor.claim()` 只要看见这条标记就跳过整个不确定性闸门。
标记既未点名任何调用，也不计数，于是产生两个后果。在确认*之后*才变得不确定的操作不会再被追问：
工作越过了一个无人确认的外部效果继续执行。而由于标记只存在于索引行上，任何一次行重写——尤其是从会话日志
重建索引的那一次——都会重新裁定人类已经回答过的问题。许可的*记录*变成了许可本身，而这个组件自己的文档
写得很清楚：索引只是派生数据，日志才是权威。

**仍未结束的调用被记成了疑问。** 待办调用窗口容纳 22 个标识，而投影为每一个被窗口挤出的调用当场记下一条
未知结果疑问——那时它仅仅是*尚未结束*。随后结果路径在标识已不在窗口内时原样返回状态，于是这条疑问再也无法
撤销。因此一次并发数超过 22 的步骤，会为那些其实已经成功结束的调用留下永久疑问，把任务挂起来等人工复核一个
并不存在的疑问。这在正常执行中就会发生，并且恰恰更容易出现在又宽又长、正是恢复机制所要服务的那类任务里。

## 决策

裁决是关于任务的事实，因此与任务一同记录：`MissionSnapshot.uncertainAcknowledged` 记下上一次裁决覆盖了多少条
已记录的未知结果，随会话日志一起折叠，且永不缩小——`fold.ts` 会拒绝收窄该水位或把它丢弃的变更，连带抓住那些
悄悄丢掉该字段的写入路径。`resume()` 以 `max(旧值, 已记录数)` 写入水位；索引行上的标记仍然写入，但只作诊断，
任何闸门都不再读取它。

服务与闸门把「还剩哪些疑问」交给一个纯函数：`src/uncertainty.ts` 中的 `unacknowledgedUncertainty(operations,
unlisted, acknowledged)` 用已覆盖的前缀减去已记录的疑问并返回余下的部分，同时把有界窗口无法点名的那些保留在
`unlisted` 里。水位落在 `[0, 已记录数]` 之外时一条都不清除——与真实裁决不对应的状态不可能放行工作。该函数不依赖
服务也不依赖运行时，因此两个调用方共用同一套算术，却无需互相引入。

对被挤出的调用仍然只做*计数*，且仍在同一份投影状态上：`MissionProjectionState.pendingOverflow` 是窗口没容纳下的
未结束调用数，调用被挤出时加一，而当窗口已不再列出的标识迎来结果时减一。只有已提交的结果自己声明「结果未知」时才记疑问。
本次修复没有引入第二套未结束调用登记表——一个有界窗口、旁边一个计数，实时路径与重放路径共用同一套严格折叠。
缓存的投影状态升到 `stateVersion: 2`，因此变更前折叠出的状态会被丢弃并从日志重读，而不是继续被信任。

## 备选方案

**保留标记，另外把已确认的标识列表附加上去。** 一份被清除的 `callId` 列表看似精确，但两类情况会破：窗口无法点名的
疑问永远无法在清单里被点名，于是永久阻塞；而有界列表把已确认的标识挤出时，会重新打开人工已经裁决过的工作。
一个单调计数对窗口如何限界、如何挤出始终保持不变。

**当某个标识迎来确定结果时撤回对应疑问。** 已否决。已记录的未知结果是日志的事实，仅因为*某条*同标识的后续结果
看似正常就清除它，会抹掉一条已被确认的疑问。只有「仍未结束的调用数」可以这样被结清。

**再用一个有界列表跟踪未结束调用。** 按本任务自身的指示否决，也按利弊否决：第二个列表需要自己的挤出规则，而那正是
我们要修的缺陷类别。计数不需要额外规则——让它减一的事件，本就与让它少一项的事件相同。

**每当出现新疑问就把水位重置。** 已否决：水位必须能在任意写入与重建顺序下存活，而「每来一条新疑问就重置」等于让
*模型*靠继续产出工作去挪动人类做出的裁决。

## 影响

[uncertainty-acknowledgement](../../../../packages/mission/mission-continuity/tests/uncertainty-acknowledgement.spec.ts)
承载确认语义的场景，包括跨进程边界并从磁盘重建恢复索引的那一条；
[wide-fanout-calls](../../../../packages/mission/mission-continuity/tests/wide-fanout-calls.spec.ts)
以 10、30、40 个同时调用驱动真实的 agent 循环，并钉住有界窗口会产生的各种折叠顺序。本次新增的十七条测试里，
十三条在修复前的源码上失败；通过的四条是有意设置的对照（窄到能放进窗口的步骤、已记录未知结果绝不被撤回的规则、
无匹配结果什么也不结清，以及此前已修好的诊断长度预算）。本包 136 条单元测试通过，每个源文件的语句、分支、函数
覆盖率均为 100%，而用 `SIGKILL` 杀死活跃任务进程那条端到端通道仍是 7/7。

一次裁决覆盖的是*最近* N 条已记录疑问，而不是任选的子集，因此对超大扇出的部分确认会就最早的若干条再次追问——
这是保守方向，而且挂起消息会先给出总数再给出名字。由于 `tool/call` 可能重复标识，一条被挤出的重复调用最多让已记录
总数多一，代价是多一次裁决；它不会提前放行任何东西。有界窗口本身带来的不精确也仍然保留：当一条被挤出的调用结清时
窗口里还留着更早的具名疑问，单条挂起消息里的名字可能错位一个位置；计数保持准确，下一次裁决即会重新对齐。
